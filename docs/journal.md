# Journal

What was built, what was learned, and any problems. Two or three lines per slice.

## 2026-11-10 (day 1)
- **Skeleton.** Set up the repo with `.gitignore` and `.env.example` before the first commit, so secrets and `data/` can never be tracked. Seeded `decisions.md` with five decisions. Learned that `.gitignore` only stops git from starting to track a file, so the order matters.
- **Python and venv.** Chose the installed Python 3.15 over installing 3.12, after confirming that every approved package has a prebuilt wheel (`--only-binary=:all:`). Pinned exact versions in `requirements.txt`. Learned that a venv is a project-private Python, and that pinning makes the install reproducible.
- **check.sh.** Added a pre-commit check script: lint, tests, a secret scan over tracked and untracked (non-ignored) files, and a frontend step that turns on once `frontend/` exists. Learned that `set -e` would treat pytest's "no tests" exit code 5 as a failure, so that one code is handled explicitly. Tested the scan with a fake key: it failed in a normal file and was ignored in the gitignored `.env`, as intended.
- **FastAPI /health.** Added `config.py` (pydantic-settings reads `.env`) and `main.py` with CORS that allows only `FRONTEND_ORIGIN`. Tests cover `/health` and that other origins are blocked. Learned that a `create_app(settings)` factory keeps tests independent of my local `.env`, and that ruff needs `src` set to know which imports are our own. Replaced a Starlette deprecation warning by adding `httpx2`, after confirming it is the package Starlette's own code imports and not a lookalike name.
- **Template loader.** Added Pydantic models for templates, a placeholder VVS list (7 requirements, `reviewedBy: null`), and a loader that stops the app from starting if any template is invalid. Wrote the tests first and ran them before the code existed. They failed with an import error during collection, which is the expected "red" step: it shows the tests really run and are not passing by accident. Decided to keep requirement codes stable, since findings will point at them, and noted storing the template version on findings as a later data model question.
  - **Where each check lives depends on what it can see.** Field rules (`min_length=1`, the `id` pattern) look at one value. `model_validator(mode="after")` runs once the whole template is parsed, so it can compare requirements with each other: no duplicate codes, and every code starts with the template prefix (`VVS-`). The loader handles what a single model can't know: that the `id` matches the filename, and that the folder has at least one template. `extra="forbid"` turns a typo like `"mandatroy"` into an error instead of a silently dropped field.
- **Next.js frontend.** Created the frontend with `create-next-app`. The home page calls `/health` from the browser through a zod-checked API helper in `lib/api.ts`, with Vitest tests for ok, bad shape, non-JSON, HTTP error, and network error. Learned that CORS is only enforced by browsers, so a client-side fetch is what really tests the backend's one-origin rule. Approved ESLint and recorded `@tailwindcss/turbopack`, both generated by the scaffold.
  - **`/code-review` found six issues**, two of which would have broken `check.sh`: the env-file guard flagged our own `.env.local.example`, and `tsc` failed on a fresh clone because `LayoutProps` comes from files that only `next dev` generates (fixed with `next typegen`). Learned to test fresh-clone conditions by deleting generated files before running checks.
- **Security review (Stage 1).** `/security-review` can't run without a git remote (it diffs against `origin/HEAD`), so I did the review by hand: no vulnerabilities. One hardening fix: `FRONTEND_ORIGIN` must now be a single `scheme://host[:port]`, so `*` or a trailing slash stops startup instead of quietly opening or breaking CORS.

## 2026-11-11 (day 2)
- **Stage 2, built overnight on a branch, reviewed in the morning.** Slices 2.1 to 2.4 were built unattended, with one commit per slice after `./check.sh`. Learned that working this way turns building into reviewing, so the per-slice summary (`docs/overnight-2026-11-10.md`) mattered as much as the code.
- **Upload checks.** Checks run cheapest first (size before parsing), the file bytes decide whether it's a PDF, and every encrypted PDF is rejected. Files are stored under UUID names.
- **Text extraction.** One string per page, NFC-normalized so that "ä" always compares equal. A scanned page gives "" instead of an error.
- **Redaction.** Personnummer and samordningsnummer are hidden in many formats, and the date check keeps org numbers safe. After review I asked for uncertain cases (wrong checksum, odd layout, split across pages) to be marked `[POSSIBLE PERSONNUMMER]` and noted, so the PM can check the original. Phone numbers stay available in the original PDF. Learned how the Luhn checksum works and why it's a signal, not proof.
- **Eval packets.** A deterministic fpdf2 generator makes three synthetic VVS packets, and a test fails if the committed packets don't match it. Packet 3 combines expired insurance with a fake personnummer for the demo.

## 2026-11-16 (day 3)
- **Reframe.** The presentation moved to Thursday, and the assignment asks for agents that achieve a business outcome. I reframed the tool as an Assessor agent, code guardrails, a Verifier agent and a human decision. Ollama is now required because simulated behaviour can't be presented as real. Cuts are logged in `docs/decisions.md`.
- **Domain checks.** Quote verification and status rules are pure code in `domain/`, with 31 tests including one that tries every combination of status, quotes and dates and asserts the result is never stronger than the model's answer.
- **Providers and prompt.** One provider interface, a simulated `scripted` provider, and an `ollama` provider. Documents go in between markers with a random token so a PDF cannot forge the end marker. A first live run on a 3B local model missed evidence that was there and invented two quotes, which the code checks downgraded to `unclear`. Lesson: quote checks stop invention, not misses.
- **Assess endpoint.** Errors are reported per file with a message and a hint, so one bad PDF does not discard the others. Scans and redactions get visible warnings. Learned that a provider outage (503) and a bad upload (400) need different advice for the user.
- **Prompt v2 and the language mismatch.** On packet 03 the local 3B model got 0 of 7 right and invented quotes, `qwen2.5:7b` with prompt v1 got 3 of 7, and with prompt v2 got 6 of 7 (packet 02 also 6 of 7). There were no false `found` in any run. The misses were all `missing` answers for evidence that was on the page. I think the main cause was a language mismatch: the requirements are written in English and the documents are in Swedish, so a small model searching for "F-skattsedel" or "hot work certificate" did not connect it to "godkänd för F-skatt" or "heta arbeten". v2 tells the model to match on meaning, to use the Swedish evidence hints as search terms, to allow `missing` only after checking every page, and repeats the task after the documents. Lesson: the quote check stops invented evidence but cannot catch a wrong `missing`, because a miss has no quote to verify. Only evals catch that. These are single runs on a small model, so they show the method, not production quality.
- **Database and workflow endpoints.** All five tables, projects, engagements and document upload. Only redacted text is stored. DecisionLog is protected by a flush hook that raises on update or delete. Known limit: raw SQL against the file would bypass it; a database trigger would be needed.
- **Assess-all and decisions.** All requirements are assessed before anything is saved, so a provider outage leaves no half-run. Re-assessing adds new findings instead of overwriting, and a PM decision stays with the finding it was made on, because carrying it onto new evidence would be a sign-off the human never gave.
- **Review UI.** Three screens (projects, project, engagement) with upload, assess, findings, decisions and decision history, all validated with zod. Status wording is in one file with a test that bans verdict words. Next.js 16 needs a `loading.tsx` beside any page that reads `params`, or the production build fails. SQLite drops timezones, so timestamps arrive without a `Z` and a small helper treats them as UTC.
- **Injection packet, and a gap it exposed.** Packet 04 is packet 02 plus a page that tells an AI to mark everything as found. On `qwen2.5:7b` there were no false `found`, but the model was swayed on VVS-05 and quoted the injected sentence as its evidence. That quote passes verification because it really is on the page. Only the expiry rule (no date in the quote) turned it into `unclear`, which was luck: the same attack on a non-expiring requirement would stay `found`. Lesson: quote verification proves a quote exists, not that it supports the requirement. A second check that reads the requirement and the quote together (the Verifier agent) is what closes this.
- **Verifier agent.** A second model call reads only the requirement and the verified quotes and says whether they support it. It can only turn `found`/`partial` into `unclear`, and if it fails it changes nothing. Probed directly on `qwen2.5:7b`: 12 of 12 injected or vague sentences rejected, 4 of 4 real quotes accepted, 2 of 2 mismatched pairs rejected. Learned that even at temperature 0 the assessor gave different answers on the same packet in two runs, so one run proves little.

## Troubleshooting notes
- **CORS: only one frontend origin.** The backend accepts browser calls only from `FRONTEND_ORIGIN` (default `http://localhost:3000`, set in `.env`). If another project is already using port 3000, Next.js starts on 3001 instead. The UI then gets CORS errors in the browser console ("blocked by CORS policy"), even though `curl` and `/docs` still work. Fix: stop the other project, or set `FRONTEND_ORIGIN` to the new port and restart the backend. `localhost` and `127.0.0.1` count as different origins, too.
